# План интеграции плат экосистемы с Home Assistant

## Цель

Переносить данные и возможности плат экосистемы в Home Assistant через единый модуль `MY_HOME`: передавать параметры и события по WebSocket и HTTP, централизованно управлять настройками, выполнять бэкапы и следить за состоянием плат.

Отопление — один из профилей устройств, но не основа архитектуры. Общая модель должна одинаково работать для плат отопления, освещения, вентиляции, безопасности, датчиков и других контроллеров.

Основной принцип: WebSocket — основной постоянный канал обмена, HTTP — канал запросов, snapshot, настроек и сервисных операций. Плата, транспорт, база и Home Assistant работают через единый внутренний слой состояния, команд, конфигурации и диагностики.

### Граница ответственности

Прошивка плат в рамках этой задачи не изменяется. Ограничения и особенности существующего протокола обходятся в модуле `MY_HOME`:

- нестабильные или смешанные типы значений нормализуются адаптером;
- физические блоки платы преобразуются в логические устройства HA;
- служебные WS-сообщения фильтруются на входе;
- отсутствие подтверждения команды компенсируется контролем результата и повторным чтением через HTTP;
- отсутствие метаданных дополняется данными `/info`, `/values` и конфигурацией модуля;
- ограничения формата `/values` не требуют изменения платы;
- физические связи и особенности платы не переносятся в пользовательскую модель HA напрямую.

Изменения прошивки допускаются только отдельной задачей и только если ограничение невозможно безопасно обработать в `MY_HOME`.

## 1. Статистически собрать контракт данных платы

Сначала собрать статистику по фактическим данным, которые платы уже отдают через HTTP `/values` и WebSocket: список параметров, типы, диапазоны, частоту изменений, повторяющиеся структуры, ошибки и варианты представления. Контракт нужно формировать на основании реальных данных нескольких плат, а не только предположений по одной плате.

Результатом должен стать единый нормализованный контракт, который не ломает уже существующие варианты данных и позволяет постепенно добавлять новые типы параметров.

Минимальная модель значения:

```json
{
  "code": "climate.boiler_temperature",
  "name": "Температура котла",
  "value": 62.4,
  "type": "sensor",
  "unit": "°C",
  "device_class": "temperature",
  "state_class": "measurement",
  "read_only": true,
  "updated_at": "2026-11-04T12:00:00Z"
}
```

Для каждого значения желательно иметь:

- стабильный `code`;
- отображаемое имя;
- тип значения;
- единицу измерения;
- допустимый диапазон;
- направление: только чтение или чтение/запись;
- класс устройства Home Assistant;
- физический блок на плате;
- логическую группу в HA;
- версию формата данных.

Для управляющего значения:

```json
{
  "code": "climate.boiler_power",
  "name": "Котёл",
  "value": true,
  "type": "switch",
  "read_only": false
}
```

## 2. Разделить физическое представление платы и логическое представление в HA

На стороне `my_home`:

- физическое устройство — один контроллер платы;
- физические блоки — реальные группы каналов и параметров на плате;
- логические устройства — объекты, которые должны появиться в Home Assistant;
- параметры — значения и команды платы;
- схема представления — правила связывания физических параметров с логическими устройствами;
- профиль — описание логической модели для конкретного типа оборудования;
- конфигурация — настройки подключения, отображения и поведения;
- диагностика — связь, ошибки, версия, нагрузка и доступность.

Физическая структура платы не должна напрямую определять структуру устройств в HA. Например, на плате могут быть один физический блок из четырёх реле и отдельный блок из четырёх АЦП. В HA это может быть представлено как четыре логических устройства, где каждое устройство объединяет одно реле и один АЦП, потому что каждое соответствует отдельной нагревательной камере.

Пример преобразования:

```text
Физическая плата
├── Блок реле: relay_1 ... relay_4
└── Блок АЦП: adc_1 ... adc_4

Логическое представление в HA
├── Камера 1: relay_1 + adc_1
├── Камера 2: relay_2 + adc_2
├── Камера 3: relay_3 + adc_3
└── Камера 4: relay_4 + adc_4
```

В интерфейсе нужен явный механизм организации перехода от физического представления к логическому:

- показать физические блоки и доступные параметры;
- создать или выбрать логическое устройство;
- связать параметры разных физических блоков;
- переименовать и настроить логическое устройство;
- проверить, что параметр не используется дважды без предупреждения;
- сохранить схему представления;
- переключать вариант представления без потери данных платы;
- показывать результат до публикации в HA.

Профили отопления, освещения и других подсистем должны быть конфигурацией, а не кодом, жёстко зашитым во frontend или транспортный слой.

## 3. Нормализовать получение данных

Переосмыслить и собрать уже существующую логику в единый слой `DeviceStateProvider`, который:

- получает полный snapshot через HTTP `/values`;
- принимает изменения и подтверждения через WebSocket;
- использует HTTP для повторного чтения состояния и восстановления после разрыва WS;
- поддерживает MQTT только как дополнительный совместимый источник, если он нужен конкретной плате;
- преобразует все источники к одному событию:

```text
device_state_changed(device_id, parameter_code, value, timestamp, source)
```

Источники данных не должны напрямую обновлять Home Assistant или UI.

Перед реализацией нужно найти существующие обработчики `/values`, WebSocket, состояния и обновления UI, убрать дублирование и оставить одну понятную цепочку преобразования данных. Транспорт, нормализация, хранение и публикация должны быть разделены небольшими ответственными компонентами с человекочитаемыми именами.

Также нужен единый слой `DeviceCommandDispatcher` для команд в плату:

```text
Home Assistant / UI
        ↓
внутренняя команда
        ↓
WebSocket (HTTP fallback/service API)
        ↓
плата
        ↓
подтверждение / ошибка
```

## 4. Синхронизация платы с модулем

Для каждой платы реализовать:

- первичную загрузку HTTP `/values`;
- сохранение параметров и метаданных в БД;
- обновление значений через WebSocket;
- обработку offline/online;
- переподключение;
- защиту от устаревших сообщений;
- принудительное обновление snapshot;
- обнаружение добавленных, изменённых и удалённых параметров.

Для каждого параметра хранить источник, время последнего обновления, качество значения и ошибку, если она есть.

## 5. Простая и понятная модель интеграции с Home Assistant

Частично начатую интеграцию нужно проверить и переосмыслить так, чтобы пользователь видел простую логическую модель, а не внутреннее устройство платы. Создать отдельный слой `HomeAssistantDeviceAdapter`, который будет:

- создавать HA device;
- создавать entities по логическому представлению;
- связывать entity с `device_id` и `parameter_code`;
- публиковать состояния и доступность;
- принимать команды из HA;
- обновлять метаданные сущностей;
- удалять устаревшие entities по управляемой политике;
- восстанавливать сущности после перезапуска.

Внутри модуля нужно сохранить связь `логическое устройство → физический параметр → физический блок → плата`, но не показывать её пользователю без необходимости. Основной экран должен отвечать на вопросы: что это за устройство, какие у него параметры и чем им можно управлять.

Базовое соответствие типов:

- `sensor` — температуры, влажность, давление, расход, напряжение и другие измерения;
- `binary_sensor` — аварии, наличие связи, состояния безопасности;
- `switch` — реле и двухпозиционные выходы;
- `number` — уставки, лимиты и числовые настройки;
- `select` — режимы и перечисления;
- `button` — сервисные команды;
- `text` — текстовые настройки;
- `update` — доступная версия прошивки;
- `climate` — только для профилей, которым действительно нужен термостатический интерфейс.

## 6. Централизованная работа с настройками

Настройки платы должны быть доступны через единый сервис конфигурации:

- чтение текущей конфигурации;
- изменение одной настройки;
- пакетное изменение настроек;
- валидация типа и диапазона;
- применение с подтверждением;
- отображение результата и ошибки;
- фиксация истории изменений;
- разграничение параметров чтения и записи.

Нужно разделить:

- настройки самого модуля `MY_HOME`;
- настройки подключения;
- настройки платы;
- пользовательские профили и сопоставления с HA.

## 7. Проверить и переосмыслить бэкапы и восстановление

Проверить существующую реализацию и сохранить только понятный пользователю сценарий. Для каждой платы предусмотреть:

- ручной backup конфигурации;
- хранение версии формата;
- дату, источник и описание backup;
- проверку целостности;
- скачивание backup;
- восстановление с предварительной проверкой совместимости;
- безопасный откат при ошибке применения.

Перед восстановлением показать состав изменений и запросить подтверждение. Бэкап должен включать настройки и профиль сопоставления, но не должен без явного указания включать секреты и токены.

## 8. Мониторинг здоровья плат

Собрать единый health model:

- доступность платы;
- состояние WebSocket и HTTP API;
- время последнего сообщения;
- время последнего полного snapshot;
- версия прошивки и конфигурации;
- ошибки и коды неисправностей;
- напряжение, температура и нагрузка — если плата их предоставляет;
- счётчики переподключений;
- задержка команд и процент ошибок;
- заполнение памяти и состояние файловой системы — если доступны.

В Home Assistant это может быть представлено как диагностические entities и атрибуты устройства.

## 9. Команды и надёжность

Команды должны:

- проверять тип и допустимый диапазон;
- иметь timeout;
- подтверждаться ответом платы;
- возвращать ошибку в HA и UI;
- не отправляться на offline-устройство;
- логироваться с источником команды;
- иметь защиту от повторной отправки;
- не создавать цикл `HA → плата → HA`.

Нужно предусмотреть версии или timestamps сообщений, last-known-state, ограничение частоты обновлений и очередь только для тех команд, для которых безопасно отложенное выполнение. После разрыва WebSocket состояние нужно сверять через HTTP `/values`.

## 10. Ручное подтверждение изменений в HA

Система не должна автоматически добавлять или удалять логические устройства и сущности в Home Assistant. Она может определить изменения и отправить уведомление, но решение принимает пользователь.

При подготовке изменений:

1. получить HTTP `/values` и метаданные;
2. сравнить их с текущей схемой представления;
3. сформировать понятный список предлагаемых изменений;
4. отправить уведомление;
5. дождаться явного подтверждения пользователя;
6. только после подтверждения применить изменения в HA;
7. записать результат и статус синхронизации в UI.

При изменении параметров система может предложить:

- создавать новые entities;
- обновлять метаданные существующих;
- удалить параметры, которые действительно исчезли;
- не менять entity ID без миграции;
- явно показывать пользователю, какие устройства и сущности будут добавлены, изменены или удалены.

Для уже добавленных плат и устройств в окне поиска должна отображаться отметка. После успешного добавления отметка должна появляться сразу, без перезагрузки страницы. Аналогично нужно показывать наличие сохранённой логической схемы представления.

## 11. UI управления платами

В карточке платы добавить:

- тип и профиль устройства;
- состояние интеграции с HA;
- список параметров и сущностей;
- переключатель физического и логического представления;
- редактор схемы сопоставления физических параметров с логическими устройствами;
- понятный предварительный просмотр результата в HA;
- состояние связи и здоровья;
- последнюю ошибку;
- кнопку обновления `/values`;
- кнопку пересинхронизации с HA;
- раздел настроек платы;
- раздел бэкапов;
- кнопку удаления устройства из `MY_HOME`;
- отдельное подтверждение удаления сущностей HA.

Удаление должно быть управляемым: старое устройство можно убрать из списка модуля, а связанные логические устройства и сущности HA — удалить только после явного подтверждения. Автоматически можно только уведомить о необходимости очистки.

Тестовый контур и mock-плата пока не входят в ближайший этап и будут добавлены после стабилизации модели представлений и основных транспортных слоёв.

## Критерий готовности первого результата

Первая плата считается интегрированной, если:

1. её параметры загружаются через HTTP `/values`;
2. изменения и подтверждения приходят через WebSocket;
3. после подтверждения пользователя в HA создаётся логическое устройство;
4. значения представлены подходящими entities;
5. команды из HA доходят до платы и подтверждаются;
6. настройки можно читать и изменять централизованно;
7. доступен backup и проверенное восстановление;
8. offline, ошибки и базовое здоровье отображаются в HA;
9. после перезапуска сохраняются физическая и логическая схемы представления;
10. изменения в HA применяются только после явного подтверждения пользователя;
11. удаление платы и очистка entities выполняются явно и безопасно;
12. повторные события не создают дубли entities;
13. отопительный сценарий работает как один из профилей, не ограничивая остальные типы плат.

## План выполнения, текущая реализация и критерии готовности

### 1. Статистический контракт данных — 100%

### 13. Виртуальные устройства и порты — 100%

Виртуальное устройство — логическое устройство в Home Assistant, а виртуальный порт — его функция/entity. Виртуальный порт может быть ручным или иметь binding на физический параметр платы. Физический параметр не публикуется в HA напрямую: схема выглядит как `плата → физический параметр → виртуальный порт → виртуальное устройство → HA`.

Ключевое правило композиции: одна физическая плата не является единственным контейнером для HA. Она может быть нарезана на любое количество независимых виртуальных устройств, а один физический параметр может входить в несколько виртуальных устройств одновременно. Ограничения уникальности действуют только внутри одного виртуального устройства: один и тот же физический параметр не должен создавать дубликаты портов в одной целевой модели.

**Готово:** отдельное хранение виртуальных устройств, CRUD, хештеги и фильтрация, UI создания устройства, создание/редактирование/копирование/удаление портов внутри устройства с выбором физического источника, привязка к `device_id + physical_code`, состояние виртуального порта `online/offline`, `last_seen` и причина недоступности, копирование устройства целиком, перенос порта между виртуальными устройствами без изменения физической привязки, статусы `привязан/не найден/изменён/без привязки`, автоматическая миграция старых standalone-портов в импортированное виртуальное устройство, список физических параметров, ручная публикация в HA; входящие WS-значения платы обновляют значение и online-состояние связанных виртуальных портов, отключение платы переводит их в offline, а команды виртуального порта передаются на физический параметр через общий dispatcher.

**Критерии закрыты:** операции доступны через UI/API, публикация остаётся ручной, а старые данные переносятся без удаления и без изменения физической модели платы.

### 14. HA-представление через виртуальные устройства — 100%

Вкладка HA внутри карточки физической платы должна показывать не список сущностей для прямой публикации, а состояние виртуального представления платы. Физическая плата остаётся источником параметров и каналом выполнения команд. В Home Assistant публикуются только виртуальные порты, объединённые в виртуальные устройства.

#### Целевая модель

```text
Физическая плата
  ├── физические порты
  ├── группы портов
  └── health / sync / online
          │
          └── действие «Создать виртуальное представление»
                    │
                    ├── виртуальное устройство
                    │     └── виртуальные порты
                    │            └── binding → физический параметр
                    │
                    └── ручная публикация в HA
```

#### Что меняется в UI физического устройства

В HA-вкладке физической платы не должно быть самостоятельных операций публикации физических портов. Вместо этого отображается:

1. список виртуальных устройств, связанных с этой платой;
2. отметка у физического порта, группы и платы целиком — используется ли он в виртуальном представлении;
3. виртуальное устройство и виртуальный порт, в которые уже входит параметр;
4. состояние связи: `не используется`, `используется`, `привязка потеряна`, `изменён тип/контракт`;
5. дата последней публикации в HA и entity ID;
6. кнопка перехода к конфигурации виртуального устройства.

#### Действия преобразования

Для каждого физического объекта должны быть доступны действия:

- физический порт → добавить в существующее виртуальное устройство как виртуальный порт;
- физический порт → создать новое виртуальное устройство с одним виртуальным портом;
- один физический порт/параметр → добавить в несколько разных виртуальных устройств без перемещения или удаления предыдущих привязок;
- группа физических портов → создать виртуальное устройство с набором виртуальных портов;
- физическая плата целиком → создать виртуальное устройство или набор виртуальных устройств по выбранному шаблону;
- добавить физический параметр в уже существующий виртуальный порт как новую привязку или заменить текущую привязку;
- открыть окно конфигурации перед сохранением результата.

Операция не должна сразу менять HA. Сначала создаётся черновик виртуальной структуры, затем пользователь проверяет сопоставление, и только после отдельного подтверждения выполняется публикация.

#### Окно конфигурации

Окно конфигурации должно содержать:

- источник: плата, группа, физический параметр;
- назначение: новое или существующее виртуальное устройство;
- имя и тип виртуального устройства;
- список создаваемых виртуальных портов;
- имя, тип HA, единицу измерения и класс каждого порта;
- направление связи `только чтение` или `чтение/запись`;
- преобразование значения: scale, offset, округление, enum mapping;
- хештеги виртуального устройства;
- предупреждения о конфликте имён, занятой привязке и несовместимом типе;
- предварительный diff: что будет создано, изменено и опубликовано;
- кнопки `Сохранить черновик`, `Применить в виртуальную модель`, `Опубликовать в HA`.

#### Ограничения безопасности

- физические сущности не публикуются в HA напрямую;
- временное исчезновение физического параметра не удаляет виртуальный порт;
- удаление виртуального устройства из HA требует отдельного подтверждения;
- преобразование группы или платы не должно перетирать существующие привязки без явного выбора пользователя;
- автоматическое создание виртуальных устройств при обнаружении новых параметров запрещено;
- все операции фиксируются в истории: кто, когда, из какого физического объекта и что создал/изменил.
